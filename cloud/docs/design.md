# 青简 Cloud：设计

青简 Cloud 是青简输入法的个人扩展：一台自建服务器，配上 Mac 端的一个常驻小程序和一个 iOS 键盘。
它提供跨设备剪贴板，汇总各设备的输入历史，并用大模型补候选、修正词库、做联想，目标是尽快提高输入准确率。

2026-10-03 定下的方向，还没有实现。

## 第一原则：与上游隔离

这个仓库是 [qingjian-team/qingjian](https://github.com/qingjian-team/qingjian) 的分叉。Cloud 必须和上游各自发展：
上游怎么更新，合并时都不应该冲突，也不应该逼着 Cloud 大改。

- **不改上游的任何文件。** Cloud 的代码、文档、脚本、CI 全部放在 `cloud/` 目录下。
  合并上游时，`cloud/` 以外的部分永远直接取上游的版本。
- **独立的 Cargo workspace。** `cloud/Cargo.toml` 自带 `[workspace]`，有自己的 `Cargo.lock`。
  不加进根 `Cargo.toml` 的 `members`，所以根目录的 `Cargo.lock`、CI、提交钩子都不受影响。
- **只用数据接口和配置接入，不改输入法本身。** 输入法已经提供的接入点：
  - 本机数据目录里的纯文本文件（`input-log.jsonl`、`user-words.tsv` 等），Cloud **只读**；
  - 用户词库目录 `dicts/`，输入法会自动当作附加词库加载，Cloud 在这里放一个 `cloud.qj`；
  - 配置 `[predict] base_url`，指向 Cloud 服务器，就把现有的云联想接到了 Cloud 的大模型代理上。
- **依赖上游 crate 的地方收在一处。** iOS 键盘要直接用 `qingjian-core` 的 `Engine`，服务端要读写 `.qj` 词库。
  所有对上游 Rust API 的调用都集中在 `cloud/crates/qingjian-cloud-bridge` 这一个 crate 里。
  上游改了 API，只改这一个 crate。
- **需要改上游的，向上游提 PR，不在分叉里打补丁。** 遇到非改输入法不可的地方，就做成对所有用户都有用的通用改动提给上游，
  合进去之后 Cloud 再用（清单见文末）。在那之前，Cloud 用不改输入法的退路先顶上。
- **以后可以整体搬成独立仓库。** `cloud/` 对上游的依赖只有 path 依赖，改成 git 依赖并锁定上游的某个标签，就能单独成仓库。

## 定位

- **一人一台服务器。** 服务端开源，谁用谁在自己的 VPS 上部署。不做账号体系，不做多租户。
  服务器是用户自己的，所以数据明文保存，也同步完整的输入历史。
- **平台**：macOS 与 iOS。协议与平台无关，以后可以给 Windows 和 Linux 写同样的常驻小程序。
- **要解决的问题，按优先级排：**
  1. 跨设备剪贴板：在 A 设备复制，在 B 设备能粘贴。
  2. 大模型提升准确率：实时补候选；后台从输入日志里找出打错的地方，修正词库。
  3. 输入历史与用户词汇总到服务端，由服务端分发到各设备。
  4. 联想：上屏之后接着给中文和英文的下一个词。

## 组成

```
cloud/
├── Cargo.toml                      # 独立 workspace
├── crates/
│   ├── qingjian-cloud-proto/       # 协议类型（服务端与客户端共用）
│   ├── qingjian-cloud-client/      # 客户端：HTTP、SSE、离线队列
│   └── qingjian-cloud-bridge/      # 唯一依赖上游 crate 的地方：读写 .qj、驱动 Engine
├── server/                         # 服务端：axum + SQLite，一个二进制
├── mac-agent/                      # Mac 菜单栏常驻小程序（独立 .app，不是输入法的一部分）
├── ios/                            # iOS 主 App + 键盘扩展
├── deploy/                         # docker-compose.yml、Caddyfile、备份脚本
└── docs/
```

- **服务端**：axum 提供 HTTP，SQLite（`rusqlite`）存储。TLS 交给前面的 Caddy。
- **鉴权**：每台设备一个令牌，用 `qingjian-cloud device add <名字>` 生成。服务端只存令牌的哈希，请求时带在 `Authorization: Bearer …` 头里。
  吊销一台设备不影响其他设备。
- **数据模型**：所有数据都是追加写的操作流。服务端给每条操作分配全局递增的 `seq`，客户端记住已经拉到哪里。
  协议只有两个基本动作：「推本机的新操作」和「拉某个 `seq` 之后的操作」。

## 1. 跨设备剪贴板

和输入法无关，Mac 端由 `mac-agent` 完成，不碰输入法。

| | 复制（上传） | 粘贴（下载） |
|---|---|---|
| Mac（`mac-agent`） | 每 0.5 秒查一次 `NSPasteboard.changeCount`，变了就上传 | 收到新条目后直接写进 `NSPasteboard`，`⌘V` 就能贴；菜单栏里列出最近的历史 |
| iOS 键盘扩展 | 键盘弹出时检查 `UIPasteboard.changeCount`，变了就上传 | 候选栏第一格显示「来自 Mac：…」，点一下插入 |
| iOS 主 App | 进入前台时检查一次；分享扩展 / 快捷指令「发送到青简」 | 历史列表，点一条复制到本机 |

- **iOS 的限制**：系统不允许在后台监听剪贴板，键盘扩展也只在键盘弹出时运行。
  所以 iPhone 上复制的内容，要等下一次弹出键盘、打开主 App 或用分享扩展时才会上传。
  Mac → iPhone 方向不受影响：只要在 iPhone 上弹出键盘就会立刻拉取。联网和读剪贴板都需要用户给键盘打开「完全访问」。
- **低延迟**：Mac 保持一条 SSE 长连接（`GET /v1/clipboard/stream`），服务端收到新条目就推下来；断线重连后按 `seq` 补拉漏掉的条目。
- **跳过敏感内容**：密码管理器写剪贴板时会带标记，带标记的条目不上传：
  - Mac：`org.nspasteboard.ConcealedType`、`org.nspasteboard.TransientType`；
  - iOS：`UIPasteboard` 的 `localOnly`、`expirationDate`。
- **防回环**：`mac-agent` 写进本机剪贴板后，自己记下这次的 `changeCount`，下一次检查时跳过，不再上传。
- **内容类型**：第一期只做纯文本，单条上限 1 MB。图片和文件以后再做。
- **历史**：服务端保留最近 200 条或 30 天，删除会同步到所有设备。
- **和 Apple 通用剪贴板的关系**：通用剪贴板要求同一个 Apple ID、设备相互靠近，内容约两分钟失效，也没有历史。
  Cloud 没有这些限制，两者可以同时开着。

## 2. 输入历史与用户词汇总

- `mac-agent` 只读 `~/Library/Application Support/Qingjian/` 下的文件，**不写输入法的学习文件**：
  - `input-log.jsonl`：记住上传到的字节偏移，之后只推新增的行，附上设备名。文件被清空（变短了）就从头开始；
  - `user-words.tsv`、`user-english.tsv`：变了就整份上传，服务端按设备保存最新版本。
- 服务端把所有设备的用户词、大模型挖出来的词、纠错闭环的结果合成一本词库，经 `bridge` 写成 `.qj`。
  各设备的 `mac-agent` 下载后放进 `dicts/cloud.qj`。输入法把它当作一本附加词库加载，一台设备造的词在其他设备上也能打出来。
- **不同步词频、n-gram 等计数表。** 要合并这些表，就得改输入法的学习模块（`Learner`），这违反隔离原则。
  它们对排序的作用，暂时由纠错闭环写进 `cloud.qj` 的词频来近似（见第 3 节），以后看上游有没有合适的接口。
- **已知限制**：Mac 版输入法只在 `[dictionaries]` 配置变化时重新加载词库。目录里的文件被替换后，要切换一次输入法或重新登录才会生效。
  这一点会向上游提「词库目录变化自动重载」（Windows 版已经这样做了）。

## 3. 大模型：提升输入准确率

目标是尽快提高「首选就是我要的」的比例。大模型分两条线工作：

- **实时补候选**：快，但每次都要等网络；
- **后台纠错闭环**：慢，但改的是本地词库，之后每一次输入都受益，而且没有延迟。效果最大的是这一条，因为它只针对你实际出错的地方。

### 实时：代理

- 服务端提供 `POST /v1/chat/completions`，原样转发给配置里的上游接口，流式响应也透传，密钥只在服务端。
- 输入法这边**不用改代码**：在「云服务」页把地址填成自己的服务器、密钥填设备令牌即可。现有的云端词与整句补全直接可用。
- **跨设备上文**：服务端在转发前，往消息前面插一条合并后的近期上屏文本（缺省 256 字，来自所有设备的输入历史）。
  这一条可以在服务端配置里关掉。
- **缓存**：同一段「拼音 + 近期上文」的回答缓存起来，各设备共用。
- **记账**：按设备、按天记录 token 用量。

### 后台：纠错闭环（每天跑，也可以手动触发）

输入日志里记了每次上屏的按键、看到的第一页候选、选了第几个、翻了几页、退格重打了什么。服务端从里面找出「没打对」的地方：

| 信号 | 说明 |
|---|---|
| 选的不是第一个、翻过页 | 首选错了，用户选的才是对的 |
| 退格后重打了不同的键 | 拼音打错了，或者第一次的结果不对 |
| 上屏后马上整个删掉重选 | 选错了 |
| 回车原样上屏拼音 | 根本打不出来：缺词，或者是英文 / 专名 |

处理流程：

1. 把这些片段连同上下文成批交给大模型，问清楚用户想要的是什么：缺的词与读音、该排前面的词。
2. 结果写进 `cloud.qj`：缺的词直接加进去；该排前面的词给更高的词频。
3. **评测门槛**：发布新版 `cloud.qj` 之前，服务端经 `bridge` 用上游的 Engine 在冻结的日志上回放，
   比较「当前版本」和「新版本」的首选命中率（做法同上游 `qingjian-cli --replay`）。变差就不发布，报告留给用户看。

### 后台：挖新词

1. 扫一遍汇总的输入历史，找出反复上屏、但基础词库与用户词里都没有的片段。
2. 成批交给大模型判断：是不是一个词、读音是什么。
3. 通过的词并进 `cloud.qj`。英文的常用词、专名、技术词也一样处理。

## 4. 联想（上屏之后接着给候选）

- **iOS**：键盘是 Cloud 自己的代码，联想在 iOS 端完整实现：
  - 本地先出：用个人上屏历史统计的接续与 `bridge` 读到的语言模型，零延迟；
  - 大模型补充：停顿后请求一次续写，补在后面；
  - 中英文都做。
- **Mac**：上屏后联想要改输入法本身（Core 现在只在组句中联想），不在分叉里做，等上游。

## 5. iOS（`cloud/ios`）

- **结构**：
  - 主 App：SwiftUI，负责配置服务器、浏览剪贴板与历史；
  - 键盘扩展：通过 `bridge` 把上游 `Engine` 编译成 `aarch64-apple-ios` 静态库，用 C ABI 给 Swift 调用；
  - 两者通过 App Group 共享数据目录。
- **内存上限**：键盘扩展只有约 48–60 MB。
  - 词库和语言模型用 `.qj` 的 mmap 打开，文件映射的只读页理论上不算进上限，要真机量过才能确定；
  - 字级神经网络重排不上 iOS。
- **键盘布局**：第一期做 26 键全拼。九宫格要改上游 Core 的拼音解析，以后再说。
- **界面**：键盘与候选栏用 SwiftUI 原生绘制，不依赖上游还在 spike 阶段的渲染器，避免跟着上游的改动返工。

## 分期

| 期 | 内容 | 完成的标志 |
|---|---|---|
| 1 | 服务端骨架（设备令牌、SQLite、部署样例）+ 剪贴板 + `mac-agent` | 两台 Mac 之间复制粘贴，延迟 1 秒以内 |
| 2 | 大模型代理 + 输入历史与用户词上传 + `cloud.qj` 分发 | Mac 上不再存大模型密钥；一台 Mac 造的词另一台能打出来 |
| 3 | 纠错闭环与挖新词（含回放门槛） | 回放报告显示首选命中率上升 |
| 4 | iOS 主 App + 键盘扩展（26 键、剪贴板候选、联想） | Mac 复制，iPhone 键盘候选栏能直接贴 |
| 5 | Windows / Linux 常驻小程序、图片剪贴板 | |

## 要向上游提的通用改动

这些对所有青简用户都有用。上游合并之前，Cloud 用括号里的退路：

- Mac 版「词库目录变化自动重载」（退路：`cloud.qj` 更新后切换一次输入法）。
- 上屏后的联想（退路：Mac 暂不支持）。
- 学习数据的导出与合并接口，用于多设备同步计数表（退路：只同步用户词，词频由 `cloud.qj` 近似）。

## 还没定的

- SSE 长连接在 Mac 合盖、网络切换后的重连策略。
- 剪贴板里的富文本（RTF / HTML）是否保留格式。第一期只取纯文本。
- 服务端备份：SQLite 单文件，`deploy/` 里给一个定时拷贝的样例脚本。
