青简 Cloud 是素笺（青简输入法的云端扩展）的客户端一侧：素笺的多用户服务器，配上链进 Mac 输入法进程的同步模块和一个 iOS 键盘。

2026-10-03 定下的方向，还没有实现。

## 第一原则：与上游隔离

这个仓库是 [qingjian-team/qingjian](https://github.com/qingjian-team/qingjian) 的分叉。Cloud 必须和上游各自发展：
上游怎么更新，合并时都不应该冲突，也不应该逼着 Cloud 大改。

- **不改上游的任何文件。** Cloud 的代码、文档、脚本、CI 全部放在 `cloud/` 目录下。
  合并上游时，`cloud/` 以外的部分永远直接取上游的版本。
- **独立的 Cargo workspace。** `cloud/Cargo.toml` 自带 `[workspace]`，有自己的 `Cargo.lock`。
  不加进根 `Cargo.toml` 的 `members`，所以根目录的 `Cargo.lock`、CI、提交钩子都不受影响。
- **只用数据接口和配置接入，不改输入法本身。** 输入法已经提供的接入点：
  - 本机数据目录里的纯文本文件（`input-log.jsonl`、`user-words.tsv` 等），Cloud **只读**；
  - 用户词库目录 `dicts/`，输入法会自动当作附加词库加载，Cloud 在这里放一个 `cloud.qj`；
  - `[predict] provider` 缺省就是 `qingjian`：云联想的地址与令牌由输入法在运行时从 Cloud 的配置里拿（`qingjian_cloud_mac::llm_endpoint`），不写进会同步的 config.toml；`custom` 才用填的 `base_url` / `api_key`。
- **依赖上游 crate 的地方收在一处。** iOS 键盘要直接用 `qingjian-core` 的 `Engine`，服务端要读写 `.qj` 词库。
  所有对上游 Rust API 的调用都集中在 `cloud/crates/qingjian-cloud-bridge` 这一个 crate 里。
  上游改了 API，只改这一个 crate。
- **非改输入法不可的，做成最小的分叉补丁。** 新代码尽量放新文件，对上游已有文件只加几行挂钩；补丁清单与合并上游时的处理见 [fork-patch.md](fork-patch.md)。
  （2026-10-03 起：学习数据同步不提交上游，由自建服务器解决，因此接受分叉。）
  合进去之后 Cloud 再用（清单见文末）。在那之前，Cloud 用不改输入法的退路先顶上。
- **以后可以整体搬成独立仓库。** `cloud/` 对上游的依赖只有 path 依赖，改成 git 依赖并锁定上游的某个标签，就能单独成仓库。

### 自用的 `local` 分支

上游还没合并、但自己想先用的 PR，不合进 main。`cloud/patches.txt` 列出 PR 编号，
`cloud/scripts/build-local.sh` 每次从头生成 `local` 分支，内容是「main + 这些 PR」。

- 有冲突的 PR 会被跳过并列出来，等作者 rebase 后再试。
- 上游合并了哪个 PR，就从清单里删掉它。
- 分支每次都从头生成（加 `PUSH=1` 时强推到 origin），不要在 `local` 上直接提交。

## 第二原则：离线照样可用

断网、服务器宕机、服务器还没搭好，这三种情况必须和「没装 Cloud」一样能正常打字。Cloud 只能锦上添花，不能变成单点故障。

- **打字的路径上没有网络。** 词库、语言模型、学习数据、`cloud.qj` 都在本机，Core 不联网。
  大模型的实时补候选本来就是异步的：本地候选先出，请求失败只在后台线程记一条警告（`qingjian-predict` 的 `worker.rs`），不阻塞按键，也不弹窗。
- **大模型的成果落在本地。** 纠错闭环和挖新词的结果写进 `cloud.qj`，下载之后断网也一直有效。
  断网时少的只是实时补候选，这部分效果之前积累下来的已经在本地了。
- **各功能的退化方式：**

  | 功能 | 断网时 | 恢复后 |
  |---|---|---|
  | 打字、候选、学习 | 完全不受影响 | — |
  | 实时补候选 | 不出云端词，本地候选照常 | 自动恢复 |
  | 剪贴板 | 本机复制粘贴照常；要发出去的条目存进本地队列（落盘，重启不丢） | 队列按顺序补发；按 `seq` 补拉别的设备的条目 |
  | 输入历史上传 | 输入法照常往本机写日志 | 从上次的偏移接着上传，不丢不重 |
  | 用户词、`cloud.qj` | 用最后一次下载的版本 | 有新版本再下载 |
  | iOS 键盘 | 完整的本地引擎；没开「完全访问」时也一样 | 同上 |

- **失败要安静。** 连不上服务器时，Mac 端（`qingjian-cloud-mac`） 按指数退避重试（最长间隔 5 分钟），「中☁ → 青简 Cloud ›」里显示离线，不弹通知。
  iOS 键盘弹出时只做一次短超时（1 秒）的尝试，失败就作罢，不影响键盘出现的速度。
- **验收**：每一期都要在关掉 Wi-Fi 的情况下测一遍：打字延迟不变、没有报错弹窗；恢复网络后数据补齐。

## 定位

- **素笺多用户服务。** 服务端闭源（synon-ime），部署在 `pinyin.synon.ai`（新加坡）。
  2026-10-06 起**默认不要账号**：开通云服务的那一下就地建一个空间，空间之间数据隔离（服务端内部仍按一个用户存），
  新设备用匹配码加入并在旧设备上允许；登录（Apple / 邮箱 / 微信）只作将来的找回方式。
  每个用户一把数据密钥，敏感字段（剪贴板、学习数据、输入日志、配置）入库前加密，删账号即销毁密钥；服务端处理请求时能解密，这一点写进隐私政策。
  剪贴板、同步、输入日志、大模型四项各自单独同意、缺省全关；关掉一项即删除云端这部分数据，本机数据不动。
  Google、X 等其他登录方式以后再加。
- **开通前先取得出境同意。** 服务器在境外，第一次把数据交出去之前必须有单独的出境同意，客户端随请求带同意文本的版本号
  （`qingjian_cloud_proto::CROSS_BORDER_CONSENT_VERSION`，改了文本就换版本）；服务端缺同意或不认这个版本返回 400 `consent_required`。
  iOS 在开通页（`App/Space/CreateSpaceView.swift`）有一个默认不勾选的勾选框，没勾桥不联网；建空间与输码加入都要先勾。
- **平台**：macOS 与 iOS。协议与平台无关，以后可以给 Windows 和 Linux 写同样的常驻小程序。
- **要解决的问题，按优先级排：**
  1. 跨设备剪贴板：在 A 设备复制，在 B 设备能粘贴。
  2. 大模型提升准确率：实时补候选；后台从输入日志里找出打错的地方，修正词库。
  3. 输入历史与用户词汇总到服务端，由服务端分发到各设备。
  4. 联想：上屏之后接着给中文和英文的下一个词。

## 组成

```
cloud/
├── Cargo.toml                      # 独立 workspace
├── crates/
│   ├── qingjian-cloud-proto/       # 协议类型（服务端与客户端共用）
│   ├── qingjian-cloud-client/      # 客户端：HTTP、SSE、离线队列
│   └── qingjian-cloud-bridge/      # 唯一依赖上游 crate 的地方：读写 .qj、驱动 Engine
├── crates/qingjian-cloud-mac/      # Mac 端：链进输入法进程（2026-10-03 起，之前是独立的菜单栏常驻程序）
├── ios/                            # iOS 主 App + 键盘扩展
└── docs/

synon-ime/（独立的闭源仓库，与本检出并排）
├── server/                         # 服务端：axum + SQLite，一个二进制
├── tuner/                          # 纠错闭环
└── deploy/                         # compose、deploy.sh、备份、nginx 站点副本
```

- **服务端**：axum 提供 HTTP，SQLite（`rusqlite`）存储。TLS 交给前面的 nginx。
- **鉴权**：**默认是空间 + 匹配码**（2026-10-06）。iOS 在「我 → 素笺云服务」或引导第三步开通：`POST /v1/space` 建空间，
  或者 `POST /v1/pair/join` 拿匹配码申请加入、轮询到旧设备允许；两种都当场拿到这台设备的会话，由 Rust 桥写盘、不交给 Swift。
  出码、列申请、允许 / 拒绝在已登录的设备上做（`GET /v1/pair/requests`、`POST /v1/pair/requests/{id}`）。
  匹配码是 8 位 Crockford Base32，展示成 `K7P2-9QXM`；轮询时凭据走 `X-Pair-Secret` 请求头，不放查询串。
  **下面这段登录仍然在代码里，但 iOS 已经没有了入口**，等 Mac 那一侧一起收：
  账号登录。iOS 在主 App 的「账号」页用 Sign in with Apple（带 nonce）或邮箱 6 位验证码登录，由 Rust 桥发请求，
  会话令牌（`sjt_…`）只写进 App Group 的 `cloud.toml`、不交给 Swift；Mac 在输入法菜单里点「登录…」，用 `ASWebAuthenticationSession`
  打开服务端的网页登录页，PKCE（verifier 只在输入法进程里）换回一次性码，再换会话令牌写进 `QingjianCloud/config.toml`。
  `cloud.toml` 与 Mac 的 `config.toml` 同时存 `user_id`，用来判断是不是换了账号；都是原子写、权限 0600。
  服务端只存令牌的哈希，请求时带在 `Authorization: Bearer …` 头里；每台设备一个会话，可以在任意设备上注销别的设备。
  构建产物里不带令牌，iOS 安装包只写死服务器地址。旧的 `qjc_` 设备令牌作废，旧版用户升级后显示未登录。
- **功能开关**：`PUT /v1/consents/{feature}`，四项（`clipboard` / `sync` / `input_log` / `llm`）新用户全关。客户端切换时先问服务器，
  成功后写回本机配置（`cloud.toml` 里对应 `clipboard` / `sync` / `logs` / `llm`）。
- **登录失败的分类**（`ClientError`；iOS 桥失败返回 `{"code","message"}`，code 清单见 `qingjian_bridge.h`）：

  | 错误 | 来源 | 处理 |
  |---|---|---|
  | `AuthFailed` | 登录类接口 401：验证码错、Apple 令牌无效 | 提示重输，可重试 |
  | `NotConfigured` | 登录类接口 503：服务器没配这种登录方式 | 重试没用，换一种方式 |
  | `LockedToday` | 同一邮箱当天验证码输错 3 次后 429，code=`locked_today` | 当天不再接受，改用 Apple 登录或明天再试 |
  | `ConsentRequired` | 400 `consent_required` | 让用户重新勾选同意 |
  | `RateLimited` | 其余 429（验证码发得太勤、大模型超每日上限） | 这次放弃，稍后再试 |
  | `Unauthorized` | 已登录请求的 401：会话被注销或账号已删 | 本机显示未登录 |
  | `Forbidden` | 账号类 403：这项功能在服务器上没开（比如在别的设备上关了） | 停掉对应的那一项，等用户重新打开 |

- **各线程收到 403 / 401 时**：剪贴板上传线程清空离线队列（用户撤回了同意，攒着的明文不留），关闭期间不再入队，重新打开也不补传；
  `DataSync` 把对应项（`sync` 同时覆盖学习数据与配置两项）停掉并记进 `disabled`，`disabled` 只增不减，重新打开要重建 `DataSync`；
  401 / 403 之后每 300 秒轮询一次，是有意的：用户可能在别的设备上重新打开了这项功能，一次请求代价很低，成功了自动恢复，不是退避。
- **同步进度何时重置**：「同步」开关的值变化时，只清学习数据与配置的进度（剪贴板与输入日志的留着）；换账号登录或删号时，
  清掉整个 `cloud/`（基线留着的话，新账号服务器上是空的，会把本机学到的减掉；离线队列里是旧账号的事件，不删会传到新账号）
  和本机的输入日志（不删的话新账号一开「上传输入日志」就从偏移 0 把旧账号期间的明文全传上去）。同一账号退出再登录，进度保留。
  iOS 在换账号与删号时删 `input-log.jsonl`（及轮转副本）；Mac 的输入法一直以追加方式握着这个文件，所以是截断，再经 host 钩子让输入法丢掉写入缓冲里的旧输入并重开
  （`apps/macos` 的分叉改动见 [fork-patch.md](fork-patch.md)）。
- **数据模型**：所有数据都是追加写的操作流。服务端给每条操作分配全局递增的 `seq`，客户端记住已经拉到哪里。
  协议只有两个基本动作：「推本机的新操作」和「拉某个 `seq` 之后的操作」。

## 1. 跨设备剪贴板

和输入法无关，Mac 端由 Mac 端（`qingjian-cloud-mac`） 完成，不碰输入法。

| | 复制（上传） | 粘贴（下载） |
|---|---|---|
| Mac（Mac 端（`qingjian-cloud-mac`）） | 每 0.5 秒查一次 `NSPasteboard.changeCount`，变了就上传 | 收到新条目后直接写进 `NSPasteboard`，`⌘V` 就能贴；「中☁ → 青简 Cloud ›」里列出最近的历史 |
| iOS 键盘扩展 | 键盘开着期间每 0.25 秒（`poll` 那一拍）查一次 `UIPasteboard.changeCount`，变了就读出来上传 —— 只比值不读内容，真变了那一下 iOS 会弹一次「允许粘贴」 | 候选栏第一格显示「来自 Mac：…」，点一下插入 |
| iOS 主 App | 进入前台时检查一次；分享扩展 / 快捷指令「发送到青简」 | 历史列表，点一条复制到本机 |

- **iOS 的限制**：系统不允许在后台监听剪贴板，键盘扩展也只在键盘弹出时运行。
  键盘**开着**的时候复制，下一拍（0.25 秒）就上传；键盘收着时复制的，等下一次弹出键盘、
  打开主 App 或用分享扩展时才上传（用户反馈过「复制完要关掉键盘再打开才提示」，2026-10-07 改成自动读并上传，
  不再让用户点「发到其他设备」）。读剪贴板那一下 iOS 会弹一次系统授权「允许粘贴」——
  这个系统管着，放行的范围只是这一次的内容，新复制的内容会再问一次，做不到「设一次永久放行」。
  Mac → iPhone 方向不受影响：只要在 iPhone 上弹出键盘就会立刻拉取。联网和读剪贴板都需要用户给键盘打开「完全访问」。
- **低延迟**：Mac 保持一条 SSE 长连接（`GET /v1/clipboard/stream`），服务端收到新条目就推下来；断线重连后按 `seq` 补拉漏掉的条目。
- **跳过敏感内容**：密码管理器写剪贴板时会带标记，带标记的条目不上传：
  - Mac：`org.nspasteboard.ConcealedType`、`org.nspasteboard.TransientType`；
  - iOS：`UIPasteboard` 的 `localOnly`、`expirationDate`。
- **防回环**：Mac 端（`qingjian-cloud-mac`） 写进本机剪贴板后，自己记下这次的 `changeCount`，下一次检查时跳过，不再上传。
- **内容类型**：第一期只做纯文本，单条上限 1 MB。图片和文件以后再做。
- **历史**：服务端保留最近 200 条或 30 天，删除会同步到所有设备。
- **实现上的取舍（第 1 期）：**
  - Mac 程序用 Rust + objc2 写（和上游 Mac 壳同一套），与服务端共用 `qingjian-cloud-client`，离线队列、重连、去重都在这个 crate 里，可以在 Linux 上测试。
  - TLS：Mac 用系统的 Security.framework，信任钥匙串里的证书；Linux 与测试用 rustls。
  - ureq 没有按每次读取计时的空闲超时，读阻塞时发现不了死连接，所以每条 SSE 连接最长维持 60 秒，到时重连并按 `seq` 补拉；
    另外每次上传成功后都主动补拉一次。合盖唤醒后最多约 60 秒恢复接收。
  - 别的设备的条目只有在 2 分钟内收到才自动写进本机剪贴板；离线很久后补拉到的只进菜单里的历史，免得突然覆盖正在用的剪贴板。
- **和 Apple 通用剪贴板的关系**：通用剪贴板要求同一个 Apple ID、设备相互靠近，内容约两分钟失效，也没有历史。
  Cloud 没有这些限制，两者可以同时开着。

## 2. 输入日志汇总

- Mac 端（`qingjian-cloud-mac`） 只读输入法的 `input-log.jsonl`，记住上传到的字节偏移，之后只推新增的完整行；批号是起始偏移，断网重发服务器只收一次。
- 文件变短、或者开头几十个字节变了（清空后又写了新内容），说明用户点了「清空输入日志」：服务器清空所有设备的历史，清空代数加一；
  各设备看到代数变了，就删掉之前下载的副本。各设备本机自己的日志不动，由用户各自清。
- 别的设备的日志可选地下载到 `~/Library/Application Support/QingjianCloud/input-log/<设备>.jsonl`；
  服务器上 `qingjian-cloud export-log` 导出全部，都可以直接给 `qingjian-cli --replay`。
- 用户词、词频、n-gram 等的同步见下一节「学习数据与设置」；大模型挖出来的词以后打包成 `dicts/cloud.qj` 分发（第 3 期）。
  已知限制：Mac 版输入法只在 `[dictionaries]` 配置变化时重新加载词库，`cloud.qj` 被替换后要切换一次输入法才生效。

## 2.5 学习数据与设置

同步词频（`user.tsv`）、按输入串的选择（`user-choices.tsv`）、个人 n-gram（`user-ngram.tsv`）、敲错表（`user-typos.tsv`）、
个人英文词（`user-english.tsv`）、用户词（`user-words.tsv`），以及 `config.toml`（设置与自定义短语）。
生词本（`user-vocab.tsv`，学英语的译词记录）暂不同步。

**难点**：输入法把学习数据放在内存里，每 60 秒整份写回文件。外部程序直接改文件会被下一次写盘覆盖；两台设备的计数整表二选一又会丢掉一边。

**做法：基线 + 增量 + 收件箱。**

- Mac 端（`qingjian-cloud-mac`） 只读输入法的文件，并保存一份「基线」：上次同步后各方一致的数据。
- 本机增量 = 当前文件 − 基线，推给服务器。服务器对每个键只存合并后的当前值，每次改动给这一行一个新 `seq`。
- 别的设备的增量 = 服务器值 − 基线，Mac 端（`qingjian-cloud-mac`） 写成输入法数据目录下的 `sync/inbox.tsv`。
- 输入法（分叉补丁）每秒看一眼收件箱，有就把增量加进内存、落盘、删掉文件；Mac 端（`qingjian-cloud-mac`） 看到文件没了，再把同样的增量并进基线。
- 增量是相加的，和正在学的互不覆盖，也不需要重启输入法。计数减到 0 就删；用户词的删除带墓碑，别的设备会跟着删。
- 每一步都先落盘进度再往下走：推送断在中间、写完收件箱就崩溃，下一轮都能接着做，不重复计数。
  例外是输入法在「已落盘、还没删收件箱」之间崩溃，那一份会多加一次，概率很小。
- 同一份基线同一时刻只许一个同步实例动：iOS 上每个键盘扩展进程、每次重建引擎都起一个 `DataSync`，共用 App Group 里的基线。
  每轮先拿 `cloud/learning.lock` 的排他锁、从磁盘重读基线与进度，拿不到就跳过这一轮。2026-10 之前基线只在打开时读一次，
  两个实例各推一遍同样的本机变化，对方推的又经收件箱回来、下一轮当本机变化再推，选过一次的词每轮涨 2，真机上涨到过 2 亿多。
- 计数超过 100 万（`qingjian_core::MAX_LEARNED_COUNT`）当坏数据：输入法读文件时跳过那一行，合并收件箱时不加那条增量，
  同步端读当前文件也不认它；于是下一轮的「当前 − 基线」把差额作为负增量推回去，服务器上已有的坏数随之清掉。
- **`config.toml`** 整份按「后改的赢」：两边都改过时较新的写进去，较旧的存到 `sync/config-conflicts/`。
  输入法本来就热加载配置，这部分不需要补丁。
- **注意**：`~/Library/Application Support/QingjianCloud/data/` 里是基线，删掉它（而输入法的学习文件还在）会让本机数据被当成新增量再推一遍，造成重复计数。

## 3. 大模型：提升输入准确率

目标是尽快提高「首选就是我要的」的比例。大模型分两条线工作：

- **实时补候选**：快，但每次都要等网络；
- **后台纠错闭环**：慢，但改的是本地词库，之后每一次输入都受益，而且没有延迟。效果最大的是这一条，因为它只针对你实际出错的地方。

### 实时：代理

- 服务端提供 `POST /v1/chat/completions`，原样转发给配置里的上游接口，流式响应也透传，密钥只在服务端。
- 输入法这边：`[predict] provider = qingjian`（缺省）时，地址与令牌在运行时从 `qingjian_cloud_mac::llm_endpoint` 拿，
  只在登录了且「大模型（云联想）」开着时才有；令牌是这台设备的会话令牌，不写进会同步的 `config.toml`。iOS 同理读 `cloud.toml` 的 `llm`。
- **跨设备上文**：服务端在转发前，往第一条 system 消息后面插一条各设备最近上屏的文字（来自汇总的输入日志：上屏的字、直接打出的标点，换应用记成换行）。
  **缺省关**（`QINGJIAN_LLM_CONTEXT_CHARS=0`）：输入法的提示词本来就带光标前后的文字，多一段跨设备的文字是帮忙还是干扰，
  要用导出的日志回放比较过再决定；iOS 键盘拿不到多少应用里的上文，到时候优先在那边打开。
- **缓存**：同一段「拼音 + 近期上文」的回答缓存起来，各设备共用。
- **记账**：按用户、按天记录 token 用量，超过每日上限返回 429。

### 后台：纠错闭环（`tuner`，每小时一轮，没怎么打字就跳过）

> 2026-10-04 起停用（部署里不起它），要改成按用户跑再恢复。

做成一个独立程序 `qingjian-cloud-tuner`，对服务器来说就是一台叫 `tuner` 的设备：用自己的令牌拉汇总的输入日志与学习数据，
经服务器的代理问大模型（用量记在它名下），通过把关的修正以学习数据推回服务器，各设备经第 2.5 节的学习数据同步拿到。
不需要新的分发机制，也绕开了 Mac 版输入法不自动重载词库的问题。镜像里带上游的 `qingjian-cli` 与产品数据（data-v3），
用和输入法同一个引擎判断「这个词现在打不打得出来」、做回放。

上游输入法自己已经会学：选过的词下次优先、连着选的两个词或分几次选完的一段记够两次自动造词。
纠错闭环只做本地学习做不到的三件事：

1. **词库体检**：把用户词（自动造词、云端选中的）交给大模型，只挑出读音标错的（多音字最常见）和明显不成词的，改读音或删掉。
   新读音必须是合法音节、个数等于字数；拿不准的不改。审过的词记下来，下一轮不再审。
2. **一次就学会**：日志里一段拼音分几次选完的（`qingjian` 先选「青」再选「简」），本地要两次才造词，这里让大模型确认是个词就直接补上。
   拼音必须能拼出用户实际敲的键（全拼或简拼）。同时记一次「选过它」：按输入串的选择、词频、句首 n-gram 各加一，
   和用户自己选过一次后输入法记的一样。只记选择不够：整句候选按 n-gram 打分，不受词级选择影响，会照样排在前面（实测）。
3. **话题补词**：大模型读用户最近写的文字，列出接下来很可能还会打、但通用词库多半没有的专名与术语。
   只加现在根本打不出来的（全拼敲出来前 9 个候选里都没有）；已经在候选里的留给用户选一次就学会。

**回放门槛**：日志按上屏次数切成前 80%（找问题）与后 20%（留出）。用服务器上现有的学习数据、和加上修正后的学习数据，
各用 `qingjian-cli --replay --user-dict` 回放留出段，比较首选命中数：不变差就采纳；变差先去掉把握最小的话题补词再比一次，还变差就这一轮什么都不改。
留出段不到 30 次上屏时不做门槛，只采纳有用户实际证据的修正（体检与一次就学会），不做话题补词。

**缺省只出报告不推送**（`QINGJIAN_TUNER_DRY_RUN=true`），观察几轮报告觉得靠谱再打开。每轮的报告打印在日志里，也存在它的数据卷 `/data/reports/`。

已知的局限：留出段的上屏在服务器的学习数据里已经学过（学习数据同步在先），两边的基线一样高，门槛衡量的是修正的「增量」而不是绝对水平；
它挡得住变差，但量出来的提升偏保守。

### 上下文预测：按前文排词（2026-10-04）

同样敲 `youxiang`，「汽车」后面要「油箱」、「我现在」后面要「又想」，之前首选多半一样。素笺让候选按光标前的文字排序：

- **前文进词级排序**：会话链上没有词（句首）时，用静态语言模型把光标前最后 8 个汉字切词，取最后一两个词当上文；标点结尾视为句首，私密输入不看。
  整句 Viterbi 的首词**不看前文**（试过：回放整句会少 3 句，三种变体的对比见 `plans/2026-10-04-context-prediction.md` Task 2）。
- **「选过的次数」改加分**：拼音词级里同一输入串下选过的词，从「排在上下文得分前面」改成得分上的加分 β·ln(1+次数)，β=8，强上文翻得过只选过一次的词；
  形码保持旧规则（重码顺序靠选择置顶）。
- **知微按前文给词级候选重排**（`[model] scorers = "both"`，素笺缺省）：第一页里与首选同一结构档的前 6 个词，按
  静态分 + 0.5·(神经分 − 静态分) 换位，整句和别档的词不动。通变（按键 → 整句）与知微（前文 → 词）是两条后台线程，
  按键回调不等任何一个；常驻内存多约 67 MB（f16，CLI 实测；f32 下 141 MB；输入法进程里的实测见计划文件）。`"tongbian"` 即上游行为，切回去时知微真卸载。

**本地续写暂缓**（用户 2026-10-04 定）：知微能接着前文续写几个字（`CharScorer::continue_text`，`qingjian-cli --eval-continuation` 评测），
时延够用（CPU 上 p90 63 ms），但「头两个字与原文一致」的比例只有 5%–12%（挑最有把握的 5% 位置也才 11.5%），达不到设计要求的 60%，所以没有做显示与 Tab 接受，
Tab 的行为和以前一样。接口和评测工具留着。**重启条件**：本地续写模型在这个度量上明显更好，或者有云端补全可用。

评测（产品配置 = 通变 + 知微；对照 = 仅通变）：同拼音不同上文 404 对，有前文首选 40.3% → 70.3%；整句评测与回放的整句首选不变；
回放词首选 925/1057（原 927）。已知差距：汽车 + youxiang 时油箱第 2、邮箱第 1（待议：差距很小时给知微更大权重、选择加分按次数饱和）。

## 5. iOS（`cloud/ios`）

- **结构**：
  - 主 App：SwiftUI，负责账号登录与功能开关、浏览剪贴板与历史；
  - 键盘扩展：通过 `bridge` 把上游 `Engine` 编译成 `aarch64-apple-ios` 静态库，用 C ABI 给 Swift 调用；
  - 两者通过 App Group 共享数据目录。
- **内存上限**：键盘扩展只有约 48–60 MB。
  - 词库和语言模型用 `.qj` 的 mmap 打开，文件映射的只读页理论上不算进上限，要真机量过才能确定；
  - 字级神经网络重排不上 iOS。2026-10-06 一度让键盘启动就加载通变（48df4ff），当天撤回：Mac 上同一份 `Session` 单会话峰值
    footprint 12.7MB（不加载）→ 122.5MB（加载，CPU 推理缺省 f32）/ 64.6MB（f16），都超出键盘扩展量级；而桥里没有任何地方驱动异步重打分
    （`request_rescoring` / `poll_rescoring`），有无模型 12 条输入的前 6 个候选完全一样——占着内存、每键还多算几条路径，没有任何收益。
    C ABI（`qj_load_model` 等）与桥里的加载代码保留，以后有了合适的接法再用；键盘包不再带 44MB 的通变，设置页的「本地整句模型」开关也去掉了。
- **键盘布局**：第一期做 26 键全拼。九宫格要改上游 Core 的拼音解析，以后再说。
- **界面**：键盘与候选栏用 SwiftUI 原生绘制，不依赖上游还在 spike 阶段的渲染器，避免跟着上游的改动返工。

## 已知限制（素笺 1）

- iOS 没开「完全访问」时，学习数据与同步进度在键盘扩展自己的容器里，桥只清 App Group 里的 `cloud/`；换账号时这份清不到。
- `DataSync` 的 `Drop` 不 join 后台线程：换引擎（换账号、开关变化）只缩小了新旧线程同时存在的窗口，没有消除。
  学习数据那一项靠每轮的文件锁与重读基线不会重复计数了；配置与输入日志的进度还可能被旧线程写回。
- iOS 上同步一轮期间拿着 App Group 里 `cloud/learning.lock` 的文件锁（最多几次 10 秒超时的请求）；键盘恰好在这时被挂起，
  系统可能以 0xdead10cc 结束扩展进程。锁随进程释放，进度每步落盘，不丢数据，只是多一条崩溃报告。
- Mac 的 tick 只在输入法激活期间运行：换账号后到下一次 tick 之间，写入缓冲里最多 19 条旧账号的输入可能刷出去。
- 旧版用户第一次登录时本机没有记过 `user_id` 且 `cloud/` 里有进度，按「换账号」清一次进度与输入日志（发版说明要提）。
- Apple 登录与 Sign in with Apple 权限只能在真机上验证（团队 L9YRXEKYN2，App ID `app.qingjian.cloud` 要开 Sign in with Apple）。
