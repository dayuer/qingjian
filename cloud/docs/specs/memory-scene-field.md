# 素材的 scene 字段：客户端不再填，请服务端允许缺省（2026-10-05）

**给谁看：** 服务端（闭源仓库 `synon-ime`）。客户端这边已经定完，这份是请服务端确认一件小事。

> **这份改过两版，以这一版为准。**
> - 第一版（同一天早些时候）：「把 `scene` 从枚举改成不透明字符串」——那时客户端把场景改成了用户自建的分组。
>   服务端按这个合了（synon-ime#5），客户端 proto 也改了（青简 `cb94be8`）。
> - 第二版：「请把这个字段删掉」——客户端当天又推翻，场景整个没了。
> - **这一版（现行）**：不删字段、也不再改类型语义，只把它变成**可选**；客户端不再填。这样两边都不用再改一轮。

## 一句话

`MemoryItem.scene` 与 `ContactRegistration.scene` 改成 `Option<String>`，加上
`#[serde(default, skip_serializing_if = "Option::is_none")]`：**客户端不再填这个字段，请求里就不出现它**。
服务端只要**允许字段缺省**（反序列化时给个默认值），其余一个字都不用改。

## 为什么

客户端 2026-10-05 把「场景」这一层**整个去掉了**。经过是这样：

1. 原来是写死的三个（恋爱 / 日常 / 工作），三个场景行为还不一样；
2. 当天先改成「用户自己建、自己起名、可改可删的分组」（`memory/scenes.json`）——服务端那次跟着把枚举改成了字符串；
3. 当天又推翻：**没有场景了**。人是一张平铺的名单，键盘上左边切人、右边切技能。

现在的形态：

- 名单就是一张平铺的人（`contacts.json`），**没有分组**；
- 键盘工具栏左边切人、右边切技能；**每个人可以指定一个改写技能**（`Contact.skill`，不指定用全局默认）；
- 学习不再按场景分区，改成**按人隔离**：选了人时学到的（含新造的中文词、英文词）只进这个人的对象层，
  「不指定」时才写全局；
- 「按场景开记录」（设计稿 05 的 2f 那三个开关）作废，**上传同意改成全局一个开关**（2026-10-05 用户定）。

于是客户端**没有任何值可填**了：场景 id 这种东西不再存在，编一个出来只会污染数据。

## 请服务端做的

1. 确认服务端反序列化 `MemoryItem` / `ContactRegistration` 时**允许 `scene` 缺省**（没有这个键也能收，
   有 `#[serde(default)]` 之类的就现成了）。**这是唯一需要确认的一件事。**
2. 存储与脱敏规则里如果用了它（分区、计费、脱敏），要改成不依赖——客户端不填之后它恒为空。
   「记的是哪一类关系」已经没有这个信息了，不要从别处猜。
3. 已经入库的历史值（`daily` / `dating` / `work` 与后来的场景 id）随它去，不用迁。

## 客户端这边的现状

- proto 里这两个字段现在是 `String`（青简 `cb94be8` 删掉了 `Scene` 枚举）；这一版再改成 `Option<String>`。
  注释里指向桥的 `memory/scene.rs` 的那句会一并去掉（那个文件正在删）。
- 桥里现在**没有任何地方构造** `MemoryItem` / `ContactRegistration`（素材上传这条路径还没实现，见
  [2B 计划](../plans/2026-10-04-memory-2b-client.md)），所以这次改动不影响任何在跑的东西。
- 本机的记忆（`contacts.json`、`state.json`）里再也没有场景；旧文件里多余的 `scene` 键读时忽略、下次写盘就没了。
- 分区学习改成按人、技能跟着人走的细节见 [关系记忆](relationship-memory.md) 与
  [人 + 技能包](../plans/2026-10-05-people-and-skills.md)。
