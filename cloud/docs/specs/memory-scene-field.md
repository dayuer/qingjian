# 素材的 scene 字段：请服务端改成不透明字符串（2026-10-05）

**给谁看：** 服务端（闭源仓库 `synon-ime`）。客户端这边已经定完，这份是请服务端跟着改的一件小事。

## 一句话

`MemoryItem.scene` 与 `ContactRegistration.scene` 现在是 proto 的 `Scene` 枚举（`daily` / `dating` / `work`），
请改成**不透明字符串**：客户端传场景 id，服务端按字符串存、原样返回，**不校验取值、也不按取值分支**。

## 为什么

客户端 2026-10-05 把「场景」从写死的三个（恋爱 / 日常 / 工作）改成**用户自己建、自己起名、可改可删的分组**
（`memory/scenes.json` 里的 `{id, name}`，默认只有一个「日常」）。场景之间不再有任何行为差异，
场景只剩一层分组：通讯录按它分、键盘上按它切人。

于是对服务端来说：

- 场景的**名字是用户起的**（最多 8 个字），服务端不该认识某一串特定的名字，也不该按名字分支；
- 场景 **id 是一串小写字母数字**（老数据里的 `daily` / `dating` / `work` 也是合法值），用户改名时 id 不变；
- 「按场景开记录」（设计稿 05 的 2f 那三个开关）作废，**上传同意改成全局一个开关**（2026-10-05 用户定），不分场景；
- 工作场景原有的「不提示、中性色」也不再是服务端的事：客户端不做这种区分了。

## 请服务端做的

1. `MemoryItem.scene`、`ContactRegistration.scene` 的类型从 `Scene` 枚举改成字符串；按字符串存、原样返回，
   不校验取值，也不拿它做分支（分区、计费、脱敏规则里如果用了，要改成不依赖它）。
2. 历史值 `daily` / `dating` / `work` 仍然是合法字符串，**老数据不用迁**。
3. 如果服务端想按「记的是哪一类关系」做点什么，那是另一件事：得由客户端显式传一个新字段，
   不要从 `scene` 的取值去猜——那个值现在是用户随手起的名字。

## 客户端这边的现状

- `qingjian_cloud_proto::Scene` 枚举**还留着、没人用**：桥里现在没有任何地方构造 `MemoryItem` / `ContactRegistration`
  （素材上传这条路径还没实现，见 [2B 计划](../plans/2026-10-04-memory-2b-client.md)）。等服务端这边定了再一起改。
- 本机的记忆（`memory/scenes.json`、`contacts.json` 的 `scene`、`state.json` 的 `scene` 与 `last`）都已经是字符串场景 id，与服务端无关。
- 分区学习也不再按场景：**按人隔离**（选了人时只写这个人的对象层、不写全局、不记个人 n-gram；「不指定」时写全局），
  见 [场景计划](../plans/2026-10-05-scene-management.md)。
