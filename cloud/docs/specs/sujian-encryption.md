# 素笺：服务端可处理的数据加密

2026-10-04 起草。前提：记忆整理、分区学习、改写都要大模型读到内容，服务端处理时必须能解密，所以不做端到端加密。
目标是在这个前提下，把「谁能解、什么时候解、删了以后能不能真删干净」做严。
取代 [relationship-memory.md](relationship-memory.md)「存储与密钥」里客户端持私钥的写法；子项目 1 的 spec（synon-ime `2026-10-04-account-multitenant-design.md` §2）按本文调整。

## 防什么、不防什么

| 威胁 | 本方案 | 说明 |
|---|---|---|
| 数据库文件、备份泄露 | 防 | 全是密文，解密钥匙不在库里 |
| 运维或管理命令翻看用户内容 | 防 | 管理命令没有解密路径，只看元数据 |
| 代码 bug 把 A 的数据给 B | 防 | 密文绑定用户与列，挪过去解不开，报 500 |
| 大模型供应商留存、训练 | 防 | 只发脱敏后的文字，零留存条款 |
| 用户删号 / 关功能后数据还能恢复 | 防 | 销毁对应密钥，连旧备份一起失效（见「删除」） |
| 服务器运行中被攻破 | **不防**（第三阶段用机密计算缓解） | 处理时内存里是明文，写进隐私政策 |

## 密钥层级

```
根密钥（云 KMS 里，不出 KMS；与服务器同地域，即腾讯云新加坡）
 └─ 封装 ─▶ 主密钥 KEK（启动时向 KMS 解封，只在进程内存；带版本号，定期轮换）
             └─ 封装 ─▶ 用途密钥（每个用户、每种用途一把，随机 32 字节）
                         ├─ clipboard   剪贴板
                         ├─ sync        学习数据与配置（另派生 mac 子密钥做键去重）
                         ├─ input_log   输入日志
                         ├─ material    记忆素材（子项目 2）
                         ├─ memory      记忆卡与用户包（子项目 2）
                         └─ identity    登录身份（邮箱、Apple refresh_token）
```

- 现在的 spec 是「每用户一把 DEK、再 HKDF 派生 enc / mac」，改成**每种用途单独随机一把、单独封装**。
  这样关掉某个功能时，销毁的是那一把密钥，不只是删行，备份里的这部分数据也一起失效。
- 封装用途密钥：AES-256-GCM，AAD = `key:<user_id>:<用途>:<KEK 版本>`，存储格式前带 1 字节版本号。
- 字段加密：AES-256-GCM，每次随机 nonce，AAD = `<表名>.<列名>:<user_id>`，比现在的 `表名:user_id` 多绑定列名，同一行里两列互换也解不开。
- 子项目 1 可以先用文件里的 KEK（现状），但读取要抽象成 `KeyProvider` trait（`File` / `Kms` 两种实现），上线收费前换成 KMS。
- 内存里的密钥用 `zeroize`，不实现 `Debug`，不进日志。

## 钥匙放哪：与数据分库

**用途密钥不和数据放在同一个库里。** 现在的 spec 把 `wrapped_dek` 放在 `users` 表里，和数据一起进备份。
这样删号后，旧备份里既有密文也有封装好的密钥，主密钥还在，备份照样解得开。spec §2「备份里的密文无法解开」这句话在现状下不成立。

改法：

- `keys.sqlite3` 只存 `user_keys(user_id, purpose, kek_version, wrapped)`，与 `sujian.sqlite3` 分开存、分开备份。
- 数据库备份照旧（30 天）；钥匙库备份只保留 **7 天**。
- 删号或关功能时，先删钥匙库里的行，再删数据行。7 天后所有钥匙库备份里都没有这把密钥，数据备份里对应的密文彻底解不开。
- 隐私政策写「删除后立即不可访问，7 天内从所有备份中不可恢复」。

## 谁能解密

| 进程 | 能解哪些用途 | 什么时候 |
|---|---|---|
| `api`（在线请求） | clipboard、sync、input_log、identity、memory（读） | 处理这个用户的请求时，用完即丢 |
| `learner`（每天的批处理） | material（读）、memory（写）、sync（写） | 只处理当天开了云服务、开了对应场景的用户 |
| 管理命令 | 无 | 只能看用户数、会话数、用量这类元数据 |

- 每次解封用途密钥都记一条审计日志：时间、进程、用户、用途、原因（请求路径或批处理任务）。日志不含内容，单独保存，定期抽查，异常量要告警。
- `learner` 与 `api` 分成两个进程、两个系统账号；`learner` 不对外监听端口。

## 交给大模型之前

```
用途密钥解密（内存）
 ─▶ 规则脱敏：手机号、证件号、银行卡号、邮箱、地址 → 占位符
 ─▶ 大模型脱敏：人名、单位、具体地点 → 占位符或泛化
 ─▶ 复查：规则再扫一遍，命中就整条丢弃，只记计数
 ─▶ 发给大模型（零留存条款、国内已备案的供应商，名单测试后定）
 ─▶ 结果用 memory 密钥加密入库
 ─▶ 明文变量清零；素材原文在处理成功后删除，最多保留 7 天用于重试
```

- 大模型只看到脱敏后的文字，对象名字始终不出客户端（云端只有随机对象 id）。
- 实时的云联想（`/v1/chat/completions` 代理）同样先脱敏再转发；响应缓存的键用 SHA-256（`user_id` + 请求体）。

## 客户端

- 同步下来的人设包、用户包在本机用设备密钥加密落盘：iOS 用 Keychain，Android 用 Keystore，Mac 用钥匙串。这把密钥只管本机，不参与服务端的数据。
- 不再需要「用户私钥解封主密钥」：服务端要处理数据就必须能解，客户端持钥挡不住服务器被攻破，反而加重恢复码的负担。
  真正挡住服务器被攻破，靠第三阶段的机密计算。
- 传输：TLS 1.3，客户端固定服务端证书的公钥（pinning），防中间人。

## 分阶段

| 阶段 | 内容 |
|---|---|
| 子项目 1（现在） | 文件 KEK + `KeyProvider` 抽象；按用途分密钥；钥匙与数据分库；AAD 带列名；zeroize；解封审计日志 |
| 收费上线前 | KEK 放云 KMS；钥匙库备份 7 天；隐私政策写清楚局限、删除时限与数据存储地（新加坡） |
| 第三阶段 | `learner` 跑在机密计算环境（Intel TDX / AMD SEV 机密虚拟机），KMS 只对通过远程证明的实例放出 KEK；运维拿到 root 也读不到明文 |

## 对子项目 1 spec 的改动清单

1. §1：`users.wrapped_dek` 删掉，改为独立库 `keys.sqlite3` 的 `user_keys` 表；`sessions`、`users` 用 AUTOINCREMENT（审计发现的会话 id 复用问题）。
2. §2：每用户一把 DEK 改为每用户每用途一把；AAD 改为带列名；KEK 读取走 `KeyProvider`；加解封审计日志。
3. §2「删账号」：先删钥匙再删数据；写明备份失效的时限取决于钥匙库备份的保留期。
4. §5：关掉功能时同时销毁该用途的密钥。
5. §8 部署：钥匙库单独备份，保留 7 天；主密钥文件仍然单独备份（换 KMS 后改为 KMS 侧的密钥保护）。

## 数据存储地（2026-10-04 定）

服务器留在新加坡（腾讯云），大陆用户的个人信息属于出境。做法：

- 登录前单独取得出境同意（个人信息保护法第 39 条）：告知境外接收方（运营方自身在新加坡的服务器）、处理目的、方式、数据种类、行使权利的方式；
  不勾选不能登录，不和其他条款捆绑。同意的版本与时间记在服务端，作为留证。
- 隐私政策写明存储地与跨境传输；验证码邮件经腾讯云邮件推送发出。
- 是否还需要标准合同或申报，取决于人数与是否涉及敏感个人信息（记忆卡里可能有），**请律师确认**；生成式 AI 备案、中国区上架的 ICP 备案与存储地无关，另行办理。
