# 上文对整句首选的作用（2026-10-09）

问题：Mac 读光标前 64 字、iOS 读 `documentContextBeforeInput`，经 `set_rescoring_context` 进 Core，这段上文能帮整句首选多少。
结论：**原来是 0（整句解码从句首算）；改成「整句第一个词有条件地接光标前的词」后，同一句前半已上屏、接着打后半那种上文首选 +2.0～2.7，回放持平，冻结尺子不变。**

## 一、原来：上文没进整句解码

- 整句 Viterbi 的第一个词一律从句首 `<s>` 算；上文只给词级排序（`query/left_context.rs`）与知微的词级重排。通变（P2C）只看按键。
- 冻结的四把尺子本来就带上文（第三列，同段前面的分句），但上文全停在分句标点 / 空格 / 数字上，`left_context_of` 一律当句首，所以测不出上文。
- CLI 读题时把上文 `trim()` 掉了尾部空白：原文折行留下的「按␣␣」被当成以汉字结尾，评测接了上文而产品不会接。已改成只去行尾换行（`apps/cli/src/eval/pair.rs`）。

## 二、改法

整句第一个词接光标前最后一两个词（会话链优先；句末标点、换行、空格、数字、字母后与私密输入时仍是句首，规则同词级排序），并且三个条件都满足才采用接上文后的最优：

1. 不看上文时最优路径本来就是多词整句：整段本来是一个词（帐号、获取）时，上文的二元会把它拆成「长 + 好」「活 + 去」再当整句插到最前；
2. 接上文后的首词不比不看上文时短：上文的高频二元会把两字词拆成单字（识别到 → 是 + 别 + 到、发布到 → 发 + 不到）；
3. 静态 LM 的二元表里真有「上文末词 → 首词」（`LanguageModel::knows_pair`）：没见过的接续只是插值退回一元词频，句首统计被丢掉，高频单字胜出（痛不该、同不过、桥到）。

`static_score`（融合时被神经分换掉的那部分）第一个词也按上文算：只按句首算时，融合换掉的只有句首那一份，上文给备选路径加的分原样留下，神经分再一推就翻成错的（A4 融合回放丢的「锁死 → 索斯」就是这样，见三）。
